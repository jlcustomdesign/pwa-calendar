Server-only frontmatter page, no UI. Renders nothing.

### Login — `src/pages/login.astro`

Standalone HTML page (no layout, no ClientRouter — the inline comment at src/pages/login.astro:160-162 explains init must run on `DOMContentLoaded`). Client logic is an inline `<script>` (src/pages/login.astro:120-168) that imports `login` from `src/lib/services/authService.ts`.

Shared handler, described once:

- **`login(email, password)`** (src/lib/services/authService.ts:8-12): calls `supabase.auth.signInWithPassword({ email, password })` on the browser Supabase client (src/lib/supabase.ts:28, `@supabase/ssr` `createBrowserClient` — session persisted in cookies so the server middleware can read it). Throws `new Error(error.message)` on failure; returns `data.session` on success. Note: every Supabase error (wrong credentials, unconfirmed email, network failure, rate limit) surfaces as the same generic message downstream.

Per element:

- **`<form id="login-form" action="/dashboard" method="GET">`** (location: src/pages/login.astro:63): JS intercepts `submit` (`e.preventDefault()`, src/pages/login.astro:137-156). If JS never runs, the browser performs a native GET navigation to `/dashboard` with `?email=...&password=...` in the URL. Inputs: none directly; contains all fields below. No `novalidate`, no `autocomplete` on the form.
- **Error banner `#login-error`** (location: src/pages/login.astro:64): `<div class="hidden ...">`, text set dynamically to `Email sau parolă incorecte.` on any `login()` rejection (src/pages/login.astro:149-153), hidden again on each new submit (line 144). No `role="alert"` / `aria-live`.
- **Email input** (location: src/pages/login.astro:69-76): name `email`, type `email`, `required`, placeholder `admin@kineto.ro`, default empty. Browser-native email-format + presence validation blocks submit before JS runs. Value is `.trim()`med in the handler (src/pages/login.astro:147).
- **Password input** (location: src/pages/login.astro:84-92): name `password`, type `password`, `required`, `autocomplete="current-password"`, placeholder `••••••••`, default empty. No minlength/strength rules (server-side only). Passed untrimmed to `login()` — correct.
- **"Afișează parola" toggle button `#toggle-password`** (location: src/pages/login.astro:93-103): `type="button"` inside the password field wrapper. Toggles the password input's `type` between `password` and `text` (src/pages/login.astro:130-134). End-to-end: pure client-side state, no persistence, no metric. Issues: `aria-label` stays `Afișează parola` even when the password is visible (should invert), and the eye SVG never switches to an eye-off icon.
- **"Intră în cont" submit button** (location: src/pages/login.astro:108-113): full-width primary submit. Handler (src/pages/login.astro:137-156): `preventDefault` → disable button + set text `Se conectează...` → hide error → `await login(email.trim(), password)` → on success `window.location.replace('/dashboard')` (full reload; middleware then validates the cookie session) → on any error show `Email sau parolă incorecte.`, re-enable button, restore label. Double submit is prevented by the disabled state. Edge cases: empty/invalid fields are stopped by native validation before the handler fires; wrong password → generic error, button recovers; already-logged-in user is not redirected away from `/login` (page has no session check — public per middleware).

There is no link to `/signup`, no "forgot password" link, and no link back to `/` on this page.

### Signup — `src/pages/signup.astro`

Standalone HTML page, same visual pattern as login (blob background, centered card). Client logic is an inline `<script>` (src/pages/signup.astro:116-129). Important: despite the header comment in `src/lib/services/authService.ts:3` ("Folosit în: login.astro, signup.astro"), this page never imports or calls `signup()`.

Per element:

- **`<form id="signup-form" action="/dashboard" method="GET">`** (location: src/pages/signup.astro:50): JS intercepts `submit` (`e.preventDefault()`, src/pages/signup.astro:120-124). If JS never runs, native GET navigation to `/dashboard?fullname=...&email=...&password=...` — same credential-in-URL leak as login.
- **"Nume & Prenume" input** (location: src/pages/signup.astro:55-62): name `fullname`, type `text`, `required`, placeholder `Dr. Alex Popescu`, default empty. Native presence validation only; no length/pattern checks. Never sent anywhere (see below).
- **Email input** (location: src/pages/signup.astro:68-75): name `email`, type `email`, `required`, placeholder `alex@kineto.ro`, default empty. Same as login.
- **"Parolă" input** (location: src/pages/signup.astro:81-88): name `password`, type `password`, `required`, placeholder `••••••••`, default empty. No `minlength`, no `autocomplete="new-password"`, no confirm-password field, no visibility toggle (login has one, signup doesn't). Never sent anywhere.
- **"Creează Contul" submit button** (location: src/pages/signup.astro:92-100): primary submit with arrow SVG. Handler (src/pages/signup.astro:120-124): `preventDefault()` → `window.location.replace('/dashboard')`. That is the entire flow — no account is created, no validation feedback, no loading state, no error handling, no double-submit guard. The user lands on `/dashboard`, the middleware finds no session (src/middleware.ts:42-44) and redirects to `/login`. End-to-end this is a dead-end stub: `authService.signup()` (src/lib/services/authService.ts:15-26, which would call `supabase.auth.signUp` with `display_name` and a derived `username`) is dead code from this page's perspective.
- **"Autentifică-te aici" link** (location: src/pages/signup.astro:107): `<a href="/login">`, plain navigation to the login page. Text context: `Ai deja un cont creat?`.

Script init detail: `initSignupPage` is bound to both `DOMContentLoaded` and `astro:page-load` (src/pages/signup.astro:127-128) with no `{ once: true }` and no already-initialized guard. Harmless today (no ClientRouter on this page, so only `DOMContentLoaded` fires, and the script runs once), but if a ClientRouter is ever added, the submit listener would be bound twice.

Reachability: nothing in the app links to `/signup` (grep for `/signup` finds only the middleware public-route list and `ROUTES.SIGNUP` in constants). The page is reachable only by typing the URL — possibly intentional (admin-created accounts), but there is no in-app pointer.

### Middleware (auth/routing-relevant) — `src/middleware.ts`

Runs `onRequest` for every route. Not an interactive element, but it gates all of the above.

- **Rate limiting** (location: src/middleware.ts:12-26): for `/api/*` (60 req/min/IP) and the `/login` page (10 req/min/IP), keyed on the first value of `x-forwarded-for` (fallback `'unknown'`). Over limit → plain-text `429 Too Many Requests` with `Retry-After`. Backed by `src/utils/rateLimit.ts:6-21`, an in-memory per-instance bucket map (self-acknowledged `ponytail:` ceiling at src/utils/rateLimit.ts:1-3: resets on cold start, no cross-instance sync; also clear-all at 10k buckets). Implication for the login *page*: 10 GETs/min/IP — a handful of refreshes or a flaky PWA reload loop hits a bare-text 429 with no UI.
- **Public routes** (location: src/middleware.ts:5, 29-36): `/login`, `/signup`, `/api/auth` (note: no `/api/auth` routes exist in `src/pages/`), plus `/_astro/`, `/favicon*`, and any path ending in common static extensions pass through with no auth check. Notably `/` (index.astro) is *not* public — see below.
- **Session gate** (location: src/middleware.ts:38-46): builds a server Supabase client (`src/lib/supabaseServer.ts:27-42`, cookie-based) and calls `supabase.auth.getUser()`; on error or no user → `redirect('/login')`. This is the only real authentication check in the unit. Consequences: `/` is guarded by middleware *before* index.astro's own redirect ever runs for logged-out users (so the `else` branch in index.astro is doubly dead), and any Supabase outage/env misconfig fails closed (redirect to login; and if `PUBLIC_SUPABASE_URL`/`PUBLIC_SUPABASE_ANON_KEY` are missing, `supabaseServer.ts:23-25` throws at import time → 500 on every route).
- Client-side counterpart: the browser client also installs a global fetch interceptor (src/lib/supabase.ts:41-80) that logs Supabase 401/406 responses and auto-retries only idempotent GET/HEAD/OPTIONS requests on network errors. This affects `getUser`/auth fetches too; no automatic redirect on logout (handled elsewhere via `onAuthStateChange` in DashboardLayout, per the comment at src/lib/supabase.ts:38-40).

### 🐞 Issues found

1. **Signup flow is a non-functional stub** — HIGH. src/pages/signup.astro:120-124. Actual: submit only runs `window.location.replace('/dashboard')`; no `signup()` call, no account created; middleware then bounces the unauthenticated user to `/login`, so the flow ends in a silent dead end. `authService.signup()` (src/lib/services/authService.ts:15-26) is dead code. Expected: call `signup(fullname, email, password)`, handle success/error, create a session or route to login with confirmation.
2. **Credentials leak via GET fallback on both auth forms** — HIGH. src/pages/login.astro:63, src/pages/signup.astro:50. Actual: `action="/dashboard" method="GET"` means if JS fails/disabled/unloaded, the browser navigates with `?email=...&password=...` in the URL (browser history, server logs, Referer). Expected: `method="POST"` with a server endpoint, or at minimum no `action`/`novalidate` discipline that never lets a GET carry secrets.
3. **`isAuthenticated = true` hardcoded gateway** — HIGH (flag as suspicious hardcode, not assumed intent). src/pages/index.astro:5. Actual: constant `true`, so the "check" always redirects to `/dashboard` and the `else` → `/login` branch (line 10) is unreachable dead code; middleware does the real gating. Expected: a real session check, or an unconditional redirect with the simulated logic removed.
4. **Generic login error masks real failure causes** — MED. src/pages/login.astro:149-153 + src/lib/services/authService.ts:10. Actual: every rejection (wrong password, unconfirmed email if confirmation is enabled, network failure, GoTrue rate limit) renders `Email sau parolă incorecte.`. Expected: distinguish invalid-credentials from other errors (e.g. unconfirmed email, network), at minimum log the real error.
5. **Login page has no session check / no way in from signup discovery** — MED. src/pages/login.astro (whole page). Actual: an already-authenticated user opening `/login` stays on the login form instead of being sent to `/dashboard`; conversely nothing anywhere links to `/signup` (grep: only middleware + constants reference it), so the signup screen is URL-only. Expected (typical): redirect logged-in users away from `/login`; if self-signup is intended, link to it, otherwise remove/guard the page.
6. **`/login` GET rate limit can lock users out of the login page itself** — MED. src/middleware.ts:12-19. Actual: 10 GETs/min/IP on `/login` returns a bare-text 429 with no UI; a few refreshes or a reconnecting PWA can trip it (shared-IP users behind NAT/ school/ clinic networks especially). Expected: limit only credential-posting endpoints (Supabase GoTrue already has per-IP limits per the comment) or a higher, UI-friendly threshold.
7. **Rate-limit key spoofable / per-instance only** — LOW. src/middleware.ts:13 + src/utils/rateLimit.ts:1-3. Actual: first `x-forwarded-for` value is client-controllable where the platform doesn't overwrite it, and buckets are per-instance memory (already flagged by the `ponytail:` comment). Expected: platform-trusted IP and/or centralized limiting (the comment names Vercel Firewall / Upstash as the upgrade path).
8. **Password visibility toggle has stale affordance** — LOW. src/pages/login.astro:93-103. Actual: `aria-label` always `Afișează parola` and the icon never changes even when the password is visible; screen-reader users get a wrong label, sighted users get no state cue.
9. **Error banner not announced to assistive tech; signup lacks any feedback UI** — LOW. src/pages/login.astro:64 (no `role="alert"`/`aria-live`); src/pages/signup.astro (no error/success element at all, consistent with issue 1).
10. **Signup form missing password UX basics** — LOW. src/pages/signup.astro:81-88. Actual: no `minlength`, no `autocomplete="new-password"`, no confirm-password, no visibility toggle (login has one — inconsistent), no loading/disabled state on the button. Expected at minimum parity with login plus a strength/length hint.
11. **Signup init could double-bind listeners if ClientRouter is added** — LOW. src/pages/signup.astro:127-128: bound to both `DOMContentLoaded` and `astro:page-load` without `{ once: true }` or an init guard (login.astro:163-167 does it correctly). Harmless today, a latent double-handler bug tomorrow.
12. **Missing env vars fail the whole app at import time** — LOW. src/lib/supabaseServer.ts:23-25 (and src/lib/supabase.ts:24-26). Actual: `throw` at module load → middleware import fails → every route 500s. Expected: fail fast is arguably deliberate; but a clearer startup error and a degraded public-route mode would be safer. Noted, not assumed to be unintended.

### WeeklyCalendarCard.astro (date picker / week-month carousel)

Server-renders 60 months of weekdays (Mon–Fri) around the current month (offset −6 … +53, `:24-27`), 9 months inline and the rest inside two `<template>` elements for lazy loading (`:314-430`). "Today" is computed in the `Europe/Bucharest` timezone (`:18-20`). On Sat/Sun the active day becomes the upcoming Monday (`:31-34, 129-150`), so the header and agenda jump to next Monday on weekends (by design). Interactive surface is entirely client-side (`:435-1133`); all day buttons carry `data-year/data-month/data-date/data-full-date`.

- **Day button `[data-calendar-item]`** (location: `WeeklyCalendarCard.astro:224-248` closed strip, `:280-306`/`:339-364`/`:398-423` expanded + lazy strips): click → `selectDay(button, true)` (`:995-998`). End-to-end: clears all `data-active` marks, sets active on both the weeks-strip and months-strip instance of that date (matched via `findButtonByDate`/`findButtonByDateInMonths`, `:464-478` — boundary weeks exist in two month sections, the one whose section month matches wins), updates header `#header-date-suffix` to e.g. "Luni, 10 noiembrie" (`:767-777`), scrolls the containing strip so the week/month is centered (`:808-823`), animates the pill/circle indicators (`updatePillForButton`, `:544-673`), then persists `localStorage.selectedCalendarDate` (unpadded `y-m-d`, `:828`), sets `window.currentCalendarDate` (padded `YYYY-MM-DD`, `:826-827`) and emits `calendarDateSelected` (`emit(EVENTS.calendarDateSelected, {date})`, `:829`) → `AgendaBlock` re-renders for that date. No DB access.
- **Expand/collapse button** (label: aria-label "Comută vizualizarea lunii", location: `WeeklyCalendarCard.astro:186-190`, handler `:884-989`): toggles closed weeks carousel ↔ expanded months carousel. Finds the active date's button in the months strip, pre-scrolls the target strip, computes `--active-week-count` (weeks in the active month, fallback 6, `:922-927`) and `--active-week-offset` (week index × 3.5rem, `:872-882, 929`), flips `expanded-mode`/`closed-mode` classes + `data-expanded`, rotates the + icon 45°, morphs the active pill (600 ms), and 620 ms later re-pins the pill to the steady active button (`:981-988`). No date change, no persistence.
- **Strip drag/swipe** (location: `WeeklyCalendarCard.astro:682-731`): mousedown/touchstart on `#calendar-strip` outside any `<button>` starts a drag of the visible strip (`scrollSnapType` disabled during drag); on release it snaps to the nearest child (week or month) with a programmatic scroll (`:701-724`). Side effect: after a swipe, `handleWeeksScroll` auto-selects the day at the same weekday index in the newly centered week (see scroll entries below).
- **Weeks-strip scroll → auto date select** (location: `WeeklyCalendarCard.astro:1079-1106`, listener `:1113`): 150 ms debounce; picks the week whose span contains the strip center, then calls `selectDay` on the button with the same `data-index` as the currently active day (fallback: first day of that week). This changes the selected date — including localStorage write and `calendarDateSelected` emit — as a side effect of mere scrolling/swiping.
- **Months-strip scroll → month/year label + lazy months** (location: `WeeklyCalendarCard.astro:1108-1115`): updates `#calendar-month-year` to the nearest centered month ("noiembrie 2026", `:1053-1077`); when within half a viewport of either edge, moves 3 month sections out of the before/after `<template>` into the strip (`:494-542`), prepending with a scrollLeft compensation so the view doesn't jump.
- **Boot restore + initial emit** (location: `WeeklyCalendarCard.astro:1001-1040`): on rAF, reads `localStorage.selectedCalendarDate`; if it equals "today" it tries to re-select that button, otherwise the key is deleted (`:1019-1021`). Then unconditionally emits `calendarDateSelected` with the active (server-derived) date and positions the active pill. Guarded to run once per strip instance via `dataset.calendarAnimated` (`:447-448`).
- **Resize handler** (location: `WeeklyCalendarCard.astro:1042-1051`): re-pins the pill and the expanded month/year label on window resize (stored on `window._weeklyCalendarResizeHandler`).

On a day with an override, the modal shows values that aren't in effect and saving doesn't change the displayed break.
3. **Medium — Card „Anulare" writes status `absent`, never `anulat`**: `cancelSession` calls `markAbsent(id, 'Anulat de la card')` (DashboardLayout.astro:689-695; button at sessionCard.ts:436-444, title „Marchează ca Anulat/Absent"). `cancelAppointment` (status `anulat`) is only used for groups. Cancel vs absent statuses are effectively indistinguishable for individual sessions; the `anulat` icon/label path is dead for singles.
4. **Medium — Group drag/edit can split the group on partial failure**: `Promise.all(ids.map(updateAppointment))` (calendar.astro:777) and the group-edit submit's mixed delete/update/create batches (AddSessionSheet.astro:1168-1180) leave no rollback — one failed member row moves/updates while others don't, leaving members on different times or half-deleted.
5. **Medium — Dropping a card onto a group slot silently collides**: `updateDropTarget` only finds single-session cards (`[data-session-id]`, calendar.astro:724-726); group cards have none, so the dragged session is moved onto the group's time with no swap and no client-side overlap check — the user only learns from the DB trigger error toast, while the card has already disappeared from its old slot until re-render.
6. **Medium — Group-mode state leaks between opens**: `close()` resets the form and group-edit fields but not `isGroupSession`, `selectedPatientIds` or the toggle label (AddSessionSheet.astro:1491-1523) — after creating a group session, the next „Programare nouă" opens still in group mode (checkboxes, location selector, label `Ședință în grup activa`).
7. **Medium — Exhausted-package check reads stale source of truth**: `askRenewIfExhausted` uses `pacienti.sedinte_total/folosite` (AddSessionSheet.astro:986-988), while the calendar treats `pachet_curent` as truth (sessionCard.ts:131-164). After renewals the columns can disagree with the package table, so the renewal popup fires (or not) inconsistently with the „Abonament terminat" UI on cards.
8. **Low — Silent failure of the timeline**: any error in `renderTimeline`'s fetch block is only `console.error`'d (calendar.astro:451-453); the user sees an empty day identical to „no appointments".
9. **Low — Group creation is sequential without rollback** (AddSessionSheet.astro:1199-1209): a failure part-way leaves a partial group booked (earlier members created, later not), reported only as an error toast.
10. **Low — Dead code**: `shiftLunchBreak` defined but never called anywhere (calendar.astro:163-184); unused `upcomingDates` frontmatter (AddSessionSheet.astro:1-21); `populateDynamicContent`, `bindDateTimeSelectors`, `updateCustomTimeDisplay` bind elements that don't exist in the sheet (`#time-slots-container`, `#native-date-picker`, `#other-date-btn`, `[data-date-btn]`, `[data-time-btn]`, `#time-scroll-left`, slider/chip ids) (AddSessionSheet.astro:326-353, 468-502, 504-577); `#settings-container` toggles are null-safe no-ops.
11. **Low — Hardcoded / stale labels**: `Dr. Maria` (calendar.astro:15), `August 2026` placeholder headers (AddSessionSheet.astro:209, SessionWrapUpSheet.astro:164), dead default `Da, marți viitoare la 08:00` (SessionWrapUpSheet.astro:61), phone fallback `+1234567890` (sessionCard.ts:336), default location `Belaqva` scattered as fallback.
12. **Low — Time pickers ignore working hours**: hours hardcoded `08..23` (AddSessionSheet.astro:792, SessionWrapUpSheet.astro:1030) and `selectedTime` defaults to `08:00`; bookings outside `work_start`/`work_end` are possible and land in the timeline as continuation-style cards.
13. **Low — Lunch-time validation is a lexicographic string compare** (calendar.astro:288): works only because grid values are zero-padded; a non-padded setting like `9:00` makes any afternoon end time „invalid" (`Ora de început trebuie să fie înainte de ora de sfârșit.`).
14. **Low — Ongoing sessions can't be confirmed from the calendar page**: the `CONFIRMĂ ȘEDINȚA` button renders only after the session's end time (sessionCard.ts:526); an in-progress session has no confirm path here (wrap-up is reachable via pending-wrap-up flows elsewhere).
15. **Low — Wrap-up double re-render**: one `Confirmă` emits both `sessionsUpdated` and `patientsUpdated` (SessionWrapUpSheet.astro:574-575), and the calendar listens to both with full re-renders (calendar.astro:623-628).
16. **Low — Wrap-up time picker commits on overlay click**: `#wrapup-time-confirm` and the overlay share one handler that calls `closeTimePicker()`, which writes `customTime` (SessionWrapUpSheet.astro:380-383, 880-892) — tapping outside to dismiss still applies the picked time.
17. **Info — Swap-on-drop is undiscoverable and unvalidated**: dropping on an occupied slot swaps patients (calendar.astro:788-794) with no UI hint and no overlap/trigger check on the swap itself; surprising next to the „move" behavior. Also, `confirmIfBeyondSupply`/`lunch-overlap` use native `window.confirm`, visually inconsistent with the app's `showConfirm`/sheet patterns.
# Audit — Patients unit

Scope: `src/pages/dashboard/patients.astro`, `src/components/features/patients/{PatientList,AddPatientSheet,PaymentSheet,RenewalSheet,ShareScheduleSheet}.astro`, traced through `src/lib/services/patientService.ts` (only relevant functions), plus the shared swipe/expand controller and `window.renewSubscription` in `src/layouts/DashboardLayout.astro` (mentioned, documented elsewhere). Shared Dock / CustomToast (`showToast`, `showConfirm`) are documented elsewhere — mentioned only.

Data model notes that shape every flow below:
- All reads go through `getPatients`/`getPatient` → `applyPackageTruth` (`patientService.ts:93-134`): legacy mirror columns `sedinte_total/folosite/cost/suma_incasata/achitat` on `pacienti_view` are **overwritten** with the open package (`pachet_curent` + SUM of `plati` on it). `achitat` = legacy flag OR paid ≥ cost (the explicit flag survives even if payments don't cover the price).
- Payments are rows in `plati`, written atomically via the `record_payment` RPC (`addPayment`, `patientService.ts:287-300`).
- Renewal is the `renew_package` RPC (`resetPatientSubscription`, `patientService.ts:305-351`): closes the old `abonamente` row, opens a new one (carrying over-delivery), records the initial payment in the same transaction, then clears the localStorage renewal dismissal.
- Patient "delete" is a **soft archive** (`sters_la` timestamp, `deletePatient`, `patientService.ts:681-690`).
- First `getPatients` call per page load runs a hidden inactivity sweep (`patientService.ts:22-60`, see Issues #7).

### 🐞 Issues found

1. **HIGH — Double-counted income for `achitat` patients with `plati` rows outside the range** (reportsService.ts:30-51). `fetchAllEffectivePayments` builds `patientsWithPlati` only from in-range `plati` rows, then adds the FULL `pacienti.cost` as a synthetic payment for any `achitat = true` patient created in range who is absent from that in-range set. A patient registered in the range who paid before the range (or has only a partial in-range payment) gets their whole package cost counted again on `created_at`, on top of real `plati` sums. Expected: fallback only for patients with no `plati` rows at all (per the code comment "care nu au ÎNCĂ rânduri în tabela plati"). Corrupts `venit` for today/week/month/quarter/year and the per-day/per-segment chart distribution.
2. **HIGH — Same double-count in the income details sheet** (reportsService.ts:396-429, ReportsView.astro:653-656). `getDetailedPayments` uses the identical in-range-only exclusion, so a patient with payments outside the range appears as a full-cost "Pachet achitat" row in the chosen period; the same money is listed again in the period where the real payment lives. Worse, `openIncomeDetails` displays `expectedTotal` (the segment/card value) whenever it's >0, so the header total can silently disagree with the sum of the listed rows.

The click handler sets `currentBaseDate` but never `currentDayDate`; the selected-day highlight (`selectedStr = toLocalISOString(currentDayDate)`) therefore always marks the boot-time date, even after picking another day.
6. **MEDIUM — Escape handling breaks after the first Astro view transition** (ReportsView.astro:383-393, 1294-1344). The keydown listener is registered once under `window._reportsEscapeBound` and closes over the first script execution's `isDayPickerOpen`/`isIncomeDetailsOpen`/`isUnpaidDetailsOpen` flags; on later `astro:page-load` re-runs, new closures update different variables, so the bound listener reads stale `false` values and never fires.

### 🐞 Issues found

1. **High — Fake success on save for `backup` (and any unknown) section.** SettingsView shows "Salvează" for all sections ≠ logs (:445-455) but the submit handler has branches only for profile/schedule/break/packages/categories (:1113-1177). On `backup`, `savedSettings` stays null, nothing is written, yet the toast "Setările au fost salvate cu succes!" fires (:1184). Same for a bogus `?section=foo`, which renders an empty form whose save button no-ops with a success toast. Expected: hide the button or show a truthful toast.
2. **High — `saveProfile` event emit throws and is swallowed.** settingsService.ts:222 calls `emit(EVENTS.profileUpdated, …)` but `emit`/`EVENTS` are never imported in this file (imports at :5-6 only) → `ReferenceError` inside the try/catch at :219-224, silently dropped. The `profileUpdated` event is never dispatched — and grep shows nothing in the app listens for it anyway (dead event).
3. **High — "Șterge" wipes the cloud error log with one tap, no confirmation.** LogsView.astro:32-38 → errorLogger.ts:328 `delete().neq('id','')` removes **all** `error_logs` rows (comment: "inclusiv pe cele fără user_id"). Destructive, irreversible, zero friction. Expected: a `window.showConfirm` (CustomToast provides one) or at least a two-tap pattern.
4. **Medium — Cache reset preserves the session via a hardcoded Supabase key.** SettingsHub.astro:235-239 keeps only `sb-dlklegayibhgnrxnqapm-auth-token` — breaks if the project ref or supabase-js storage key scheme changes (silent full logout), and the choice isn't documented in the UI.
5. **Medium — Offline logout doesn't log out.** SettingsHub.astro:205-215: if `signOut()` fails (offline), the error is swallowed, only `kineto_*` keys are removed, and the `sb-*` session stays in localStorage → redirect to `/login`, but the session can be auto-restored on next load.
6. **Medium — "Eroare test" writes into production `error_logs`.** LogsView.astro:218-224 → `pushLog` → `sendLogToSupabase` insert (errorLogger.ts:240, :204-214). Test entries pollute the server-side error table; the extra `console.error` makes it two entries per tap.
7. **Medium — Empty-state copy lies under filters.** LogsView.astro:105-109 shows "Nicio eroare capturată / Aplicația funcționează fără probleme" whenever the *filtered* list is empty, even if other-type logs exist. Expected: distinguish "no logs at all" from "no logs of this type".
8. **Medium — SettingsView toast ignores its error styling.** `showToast(msg, type)` never uses `type` (SettingsView.astro:531-541): failures ("Eroare la salvare: …", :1186) render with the same green checkmark as successes. Meanwhile LogsView on the same page uses the proper shared `window.showToast` — two systems, inconsistent feedback.
9. **Medium — No cross-field validation on schedule/break.** `work_start` can be ≥ `work_end`, break can sit outside work hours or overlap it, and `zile_lucratoare: []` is happily saved (SettingsView.astro:1123-1132, :1134-1152). The calendar guards some of this elsewhere (calendar.astro:289) but the settings form doesn't.
10. **Medium — Weekend workdays are silently dropped.** Chips cover Mon–Fri only (isodow 1–5, SettingsView.astro:577-604; break chips `data-day` 1-5, :637-663). If the DB row contains 6/7 in `zile_lucratoare`/`lunch_breaks`, the UI can't display them and the next save overwrites them away.
11. **Medium — "Pauze personalizate" don't have per-day times.** All active break-day chips share one start/end pair, written identically into every active day (:1134-1152); hydration seeds from only the *first* custom entry (:626-635). The UI promises per-day customization but delivers per-day on/off only.
12. **Medium — "All categories off" cannot persist.** Hydration falls back to all-five-active when `active_categories` is empty (:791-795), so a deliberate full deactivation reloads as fully active. Also `DEFAULT_SETTINGS.categories` (settingsService.ts:27-28) omits 'Expirați' while the UI treats it as canonical — first-run defaults diverge.
13. **Low — Dead code: fake restore listener + unused imports.** `input-import-backup` doesn't exist (backup section only has the export button), yet its change handler toasts "Datele au fost restaurate cu succes!" (SettingsView.astro:544-547) — leftover from a removed import feature. `pricingService` import (:504) is never used.
14. **Low — Time-typing handlers are dead code.** Every `display-*` input is `readonly` + `pointer-events-none` (:181-189 and siblings), so the parse/auto-colon/blur-validation block (:952-1018) can never receive input — and its failure fallback would write '00:00'.
15. **Low — Time modal grid is restrictive.** Hours 08–23 and minutes 00/15/30/45 only (:865-866): 07:30 start or a :20 break is impossible from the UI even though the DB stores free `HH:MM`; a DB value outside the grid opens with no hour selected.
16. **Low — Duplicated toast system.** SettingsView renders its own `#settings-toast` (:24-31) while CustomToast (`window.showToast`) is already mounted by DashboardLayout — same page, two visuals, and the local one is the inferior one (issue 8).
17. **Low — Inconsistent defaults.** Service default `work_end` is '18:00' (settingsService.ts:19) but the view fallback is '19:00' (:573); `getSettings` null-guards lunch as '12:00'/'12:30' (:75-76) vs DEFAULT '13:00'–'14:00'; which value a first-time user sees depends on which code path fills the field.
18. **Low — Save UX: slow, no optimistic state.** `saveSettings` does select-then-write (:98-126); `saveProfile` chains up to 4 sequential Supabase calls (:168-215). On a poor mobile connection "Salvează" sits idle with no spinner/disabled state, and rapid double-taps double-submit.
19. **Low — Email change is fire-and-forget.** The email input is the only validated field (browser `type=email` blocks submit), but the actual change goes through `supabase.auth.updateUser` — may require confirmation, may fail — and failures are only warn-logged (settingsService.ts:204-206) while the UI toasts success.
20. **Low — `store._settings` is write-only; profile save emits nothing.** store.ts:19-28 holds in-memory state nothing reads (settingsService reads localStorage directly), and the profile branch never calls `setSettingsCache` (SettingsView.astro:1116-1122), so a `therapist_name` change doesn't fire `settingsUpdated` — PatientList/AddSessionSheet/calendar keep stale copies until reload.
21. **Low — `log.source` rendered unescaped.** LogsView.astro:121-123 interpolates `log.source` raw into `innerHTML`; every current call site passes constants, but it's the one field not run through `escapeHtml` while the file also shadows the shared util (:69 vs :160-167).
22. **Low — Hardcoded identity bits.** Avatar fallback initials "RV" (SettingsHub.astro:14-16), `therapist_name: 'Roxana'` default (settingsService.ts:17), and an iOS-only `alert()` text (SettingsView.astro:741) are baked into code.
23. **Low — Sparse local history, silently capped.** `MAX_LOGS = 200` (errorLogger.ts:35) drops oldest entries without any UI indication; combined with issue 3 (cloud wipe), long-term error history is fragile.

### Push API endpoints

Server push built on `web-push` (`src/lib/server/webPush.ts`): VAPID triple from env (`PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, webPush.ts:6-22); missing keys → warn + throw at send time (:37-39). Payload defaults: title "🔔 Agendă Kineto", url `/dashboard`, tag `kineto-session-alert`, TTL 24 h (:49-60).

- **POST `/api/push-subscribe`** (location: push-subscribe.ts:6-63): validates `endpoint`/`keys.p256dh`/`keys.auth` (400 otherwise), requires auth (`getUser()`, 401), upserts into `push_subscriptions` on conflict `endpoint`, stamping `user_id` + `user_agent`. The `onConflict: 'endpoint'` means an existing browser subscription is reassigned to whichever user is currently logged in on that device.
- **DELETE `/api/push-subscribe`** (location: push-subscribe.ts:65-110): requires auth; deletes row matching both `endpoint` and `user_id` (:87-91).
- **POST `/api/send-push`** (location: send-push.ts:7-83): test/confirmation sender. Builds payload from JSON body with Romanian defaults: title fallback "🔔 Notificare Agendă Kineto", body fallback "Aceasta este o notificare de test pe ecranul blocat." (:13-14). Selects **all** rows from `push_subscriptions`, optionally filtered by caller-supplied `targetUserId` (:21-26); sends in parallel; 404/410 responses collect the row ids and are deleted after the sweep (:52-66); returns `{success, sent, total, cleaned}`. No `targetUserId` → broadcasts to every registered device. Auth-wise it relies on `middleware.ts` session check only (no `getUser()` / no user scoping in the route itself).
- **ALL `/api/check-reminders`** (location: check-reminders.ts:7-170): authenticated, per-user, manual mirror of the Supabase cron (the edge function with `CRON_SECRET` is the production scheduler; this route is the user-triggerable equivalent). Computes Romania time via `toLocaleTimeString/Date` with `Europe/Bucharest` (:19-24), loads today's non-cancelled appointments (:27-39), the user's subscriptions (:42-52) and `session_duration` (default 50, :55-61). For each appointment: start alert when now ∈ [start−2, start+5] min, end alert when now ∈ [end−2, end+5] min (:74, :118). Dedup: checks the `notificari` table for a row with the same `titlu` (`🔔 Începe: {patientName}` / `✅ Final: {patientName}`) created today (:78-84, :121-127); if absent, inserts the row and pushes to every device with payload titles "🔔 Începe ședința: …" / "✅ Ședință încheiată: …", url `/dashboard/calendar` (:98-113, :139-154). Push errors are only `console.error`ed — dead subscriptions are **not** cleaned here (the edge function now handles 404/410/Apple-400 cleanup).
- **Client subscription flow** (location: pushService.ts:35-109): `Notification.requestPermission()` → wait `serviceWorker.ready` → reuse or create `pushManager.subscribe({userVisibleOnly:true, applicationServerKey: VAPID_PUBLIC_KEY})` → POST `/api/push-subscribe` → fire-and-forget confirmation push "🔔 Notificări de fundal activate!" (:91-99). Unsubscribe (pushService.ts:111-129): DELETEs the row, then `sub.unsubscribe()`. UI: "Notificări telefon" card in settings (SettingsView.astro:122-138) — badge `#notification-status-badge` states "Activ" / "Inactiv" / "Blocate" / "Nesuportat" (:689-710) and button `#btn-test-notification` toggling "Activează" → subscribe (button spinner "Se activează...") / "Dezactivează" → unsubscribe (:713-751); denial produces toast + blocking `alert()` with iOS instructions (:740-742). A duplicate activation entry point exists on the dashboard banner (AgendaBlock) and `sessionNotifier.ts` auto-asks: on the **first click/touch anywhere** in the app, if permission is `default`, it calls `requestNotificationPermission()` (:98-108), which on grant silently runs the full subscribe flow and shows a web notification "🔔 Notificări Active!" (:51-77).

### 🐞 Issues found

1. **High — `/api/send-push` broadcasts to every user.** (send-push.ts:21-26) Actual: with no `targetUserId` the route selects **all** `push_subscriptions` rows and pushes to all of them; `targetUserId` is caller-supplied with no ownership check, so any authenticated user (or session holder) can push to any/all users' devices. Expected: scope to the caller's own `user_id`, or gate broadcast behind an admin/secret check. (Middleware's session gate is the only barrier, middleware.ts:39-45.)
2. **Medium — Notification tap on an already-open app ignores the deep link.** (sw.js:163-179) Actual: if any window containing `/dashboard` exists, the SW only calls `client.focus()` — it never navigates to `notification.data.url`, so tapping "✅ Ședință încheiată" while the app sits on Setări just focuses Setări. `urlToOpen` is used only when no client exists. Expected: after focusing, `client.navigate(urlToOpen)` (or `openWindow` semantics) so the reminder's `/dashboard/calendar` target is honored.
3. **Medium — Same-day duplicate-name appointments never notify.** (check-reminders.ts:78-84, :121-127) Actual: dedupe looks up `notificari` by exact `titlu` (`🔔 Începe: {patientName}`) for today. Two appointments the same day for patients with the same rendered name (or two sessions same patient, different times) → the second appointment's start/end push is silently suppressed. The unique `notifTag` (`start_${appt.id}_${date}`) is only set as the push `tag`, never used in the DB check. Expected: dedupe key should include the appointment id.
4. **Medium — Logout leaves the push subscription attached to the old account.** (SettingsHub.astro:202-217, pushService.ts:24-33) Actual: logout clears `kineto_*` localStorage and signs out, but the browser keeps its `pushManager` subscription and the `push_subscriptions` row still points to the old `user_id`. Consequences: the device keeps receiving the previous user's session reminders until someone else subscribes; and on the next login `isPushSubscribed()` returns true (sub exists + permission granted) so settings shows "Activ" even though no row belongs to the current user (badge and reality diverge until re-subscribe upserts the row). Expected: unsubscribe-and-DELETE on logout, or at least badge check against the server row.
5. **Medium — First-touch permission prompt fires with zero context.** (sessionNotifier.ts:98-108, :51-77) Actual: the first click/touch anywhere in the app triggers `Notification.requestPermission()` and, on grant, immediately runs the full subscribe flow (permission + SW subscription + server row) plus a system notification. A user tapping anything on first load is asked for notifications before seeing any "Notificări telefon" UI. On iOS a denied prompt can only be re-enabled from Settings, making this one-shot prompt expensive. Expected: ask from the explicit "Activează" surfaces only.
6. **Low — Cache-reset preserves a hardcoded Supabase auth key.** (SettingsHub.astro:235-239) Actual: `localStorage.clear()` then restores only `sb-dlklegayibhgnrxnqapm-auth-token` — the project ref `dlklegayibhgnrxnqapm` is hardcoded; on a different Supabase project/environment the token is wiped too (surprise logout), and the ref leaks into client code. Expected: derive the key prefix from the configured Supabase URL or match `/^sb-.*-auth-token$/`.
7. **Low — New-version cache wipe deletes the live cache.** (DashboardLayout.astro:835-842, sw.js:151-159) Actual: on SW update, the app posts `CLEAR_CACHES`, which deletes **all** caches — including the current `kineto-agenda-v13` — after activation, so the running session falls back to network until assets re-cache; the `CACHES_CLEARED` reply has no listener; the message goes to `registration.active`, which during the `statechange` hand-off may still be the outgoing worker. Expected: delete only non-current caches (as `activate` already does) and skip the round-trip, or listen for the reply.
8. **Low — SW cache version is a manual constant.** (sw.js:1) Actual: `CACHE_NAME = 'kineto-agenda-v13'` must be bumped by hand each deploy; forgetting means `activate` keeps serving the old-named cache. Expected: build-time hash injection (e.g. via Astro define/vite replace).
9. **Low — Badge fetch failure falsely clears both dots.** (Dock.astro:168-171) Actual: any error in `getPendingWrapUps`/`getPatients` (offline, transient network) lands in `catch` which hides the home and patients notification dots — a failure renders as "nothing needs attention". Expected: keep previous state on failure (or retry), only hide on confirmed-empty data.
10. **Low — `showConfirm` force-cancels an open confirmation.** (CustomToast.astro:159-162) Actual: a second `showConfirm` while one is open resolves the pending promise `false` without user action — a destructive flow (delete session) awaiting confirmation silently aborts if any other code asks for confirmation. Single module-level resolver (:117) makes this global. Expected: queue or ignore the second request.
11. **Low — `deleteGroupSession` bypasses the custom confirm modal.** (DashboardLayout.astro:779-792) Actual: uses native `window.confirm('Sigur ștergi ședința în grup pentru toți pacienții?')` while sibling actions use `showConfirm` (nice Romanian modal). Inconsistent UX, no scroll-lock/before-swap handling.
12. **Low — `/` gateway is a hardcoded stub.** (src/pages/index.astro:5-11) Actual: `const isAuthenticated = true` — `/` always redirects to `/dashboard`; the unauthenticated case is dead code and the real decision lives in middleware. Harmless but misleading; any future reader trusting it breaks auth flow assumptions.
13. **Low — "Blocate" notification button still clickable.** (SettingsView.astro:701-709, :713-751) Actual: when `Notification.permission === 'denied'` the badge shows "Blocate" and the button label "Blocate", but the button is not disabled; tapping re-runs `requestPermission()` → instant 'denied' → toast + the blocking iOS `alert()` every time. Expected: disabled button with a hint, or tap opens OS settings guidance only once.
14. **Low — `/api/check-reminders` sends pushes sequentially with unlogged cleanup gap.** (check-reminders.ts:65-157) Actual: per-appointment, per-subscription `await sendPushToSubscription` inside nested loops makes the request latency grow linearly with appointments × devices; expired endpoints here only `console.error` (server row cleanup for this path relies on the newer edge-function logic, so dead rows accumulate for manual invocations). Cosmetic/perf at current scale, noted per instruction not to flag 404/410 cleanup as missing in the edge function.
